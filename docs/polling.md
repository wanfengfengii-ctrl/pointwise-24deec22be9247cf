# 轮询服务维护说明

采样器每轮读取寄存器0、1；设备数据在每个请求被处理时取值，不承诺两个寄存器来自同一瞬间。最后已知值可以继续用于显示，但不能作为当前轮次成功的凭据。本文区分**当前实现的已证实行为**、**适用边界**和**建议行为**；在发布阻塞项修复前，不能把建议行为当成现状。

## 请求身份与超时

**已证实**：事务号属于连接，分配器在 `transport.py:51-57` 跳过正在等待的编号，65535 之后从 0 继续。超时扫描（`transport.py:68-73`）把到期请求移出 pending 并给等待者 `TimeoutError`，因此已超时的请求不会再改变该轮的 future。轮次号留在应用层，设备协议只有连接内 16 位事务号、固定 unit=1 与载荷。

**已证实（缺陷）**：超时移出 pending 后，该事务号会立刻回到候选池；它不保留“迟到窗口”状态。若下一轮复用该号，而设备旧响应仍在上界内到达，接收循环（`transport.py:84-100`）会按**派发时**的 tid 把旧载荷交给新 Ticket。重放 `late_reuse` 得到新轮 `{"0":11,"1":220}`（期望 `22/220`），`paused_arrival` 在“上界内到达、上界后才派发”时同样误配。设备回复乱序时按 tid 派发只在**没有同号冲突**时成立。

**适用边界**：设备迟到上界 50tick 约束的是**响应到达**，不是客户端即时派发；`pause_dispatch()`（`transport.py:37-38,87`）可让已到达帧延后派发。因此“待上界过去，事务号即可重新使用，派发暂停不影响这条规则”这一旧说法**不成立**；旧事务号必须在“上界已过且没有未处置的到达帧”后才可释放。

**建议行为**：见 `REVIEW.md` 第 5 节。推荐保留连接并为超时事务号建立迟到隔离：expire 时保留墓碑，issue 跳过 pending 与墓碑；接收循环在 gate 之前给已到达的旧帧打标记，派发时丢弃；tid 只在 `发送tick+50` 已过且无未处置到达帧后释放。退路是超时即退役连接并要求新轮重读，但须同时修正批次成功资格。

## 批次发布

**已证实（缺陷）**：`sampler.py:22` 以 `values = dict(self.cache)` 起手，`sampler.py:33` 用 `len(values) == 2` 判 success。于是上一成功轮的缓存会补齐本轮缺失地址：部分失败轮（`partial_failure_cache`）与全部超时轮（`total_failure_cache`）都被封成 success 并写入 `publications`；连接退役导致的失败也会被旧缓存掩盖（`retire_after_success`）。`errors` 已记录失败，但**不是**仅诊断信息，它必须参与成功资格。原“两个位置均有值即可发布 success”不成立。

**已证实（对照）**：首轮无缓存时，同一设备异常会正确封为 failed 且只保留本轮部分值（`cold_failure`）；无前置成功缓存的退役轮也正确 failed（`retire_pending_round`）。这说明缺陷的必要条件是缓存播种，而不是协议校验缺失。

**适用边界**：`sources` 里的 `connection/token` 是客户端自报归属，不是设备来源证明；真实设备 seq 只能由 `evidence_gate.observed_origins` 从发帧与接收顺序还原。`protocol.py` 的数值校验只保证载荷合法，不能证明值属于本轮。

**建议行为**：只有本轮两个 ticket 都成功完成才是 success；失败轮 status 为 failed，`values`/`sources` 只保留该轮有效完成的部分值，不补入别轮缓存；失败轮不发布、不更新缓存。`cache` 可以继续用于显示，但 `publications` 与成功 `values` 不得引用缓存。已发布成功轮次无需撤回。

## 连接交接

**已证实**：`Client.close()`（`transport.py:108-113`）与接收循环 EOF/异常路径（`transport.py:102-106`）会把未完成 future 置为 `ConnectionError` 并清空 pending；关闭连接的旧响应不会进入新连接（`new_connection_isolation` 中旧 seq0 为 `delivered=false`，新连接拿到 `22/220`）。后续轮次可在新连接重新读取。

**已证实（缺陷）**：传输层“通知失败”只到 future；是否发布成功仍由 Sampler 的缓存播种与 `len(values)==2` 决定，退役轮可被旧值补成 success（`retire_after_success`）。因此“传输层已经处理失败，发布层无需另设退役规则”不成立；发布层必须独立执行批次成功资格。

**适用边界**：退役使该连接上未完成轮次失败，旧未决请求不得重试后宣称成功；重采必须使用新轮次并重新读取两个寄存器；不得永久停采。最多两轮重叠的约束不变。

**建议行为**：退役/超时后以新 `round_id` 重读 0、1；失败轮只保留本轮部分值；成功封口后更新缓存并发布。若采用连接退役方案，需明确连接建立所有权、失败传播与重试接纳；若采用事务号隔离方案，需在 transport 内维护墓碑与到达标记，不改变 `issue`/`start` 的调用方式。
